## 二、专家评审意见

### 2.1 Martin Fowler - 架构与设计

#### 🔴 CRITICAL 问题

**问题1： monolith与微服务边界混淆**

- **现状**：架构图声称"微服务架构"，但实际是一个FastAPI单体应用
- **影响**：增加不必要的分布式系统复杂度
- **建议**：
  ```
  MVP阶段应使用模块化单体架构
  服务之间通过依赖注入解耦
  为未来拆分为微服务预留接口边界
  ```

**问题2：API版本管理缺失**

- **现状**：所有接口使用 `/api/v1/`，但没有版本兼容性策略
- **影响**：未来API演进会遇到破坏性变更问题
- **建议**：
  ```
  在URL中明确版本号：/api/v1/, /api/v2/
  制定API废弃策略和迁移计划
  文档中明确版本兼容范围
  ```

**问题3：AI服务耦合度过高**

- **现状**：AIQuizService直接调用OpenAI，没有抽象接口
- **影响**：换模型需要修改业务代码
- **建议**：
  ```python
  # 引入AI Provider抽象层
  class AIProvider(Protocol):
      async def generate_quiz(self, prompt: str) -> QuizResult: ...

  class OpenAIProvider(AIProvider): ...
  class ClaudeProvider(AIProvider): ...
  ```

#### 📝 架构确认

- ✅ 当前阶段使用模块化单体架构是正确的选择
- ✅ 技术栈选择合理(FastAPI/SQLAlchemy)
- ✅ 分层设计符合标准

### 2.2 Michael Nygard - 可靠性与运维

#### 🔴 CRITICAL 问题

**问题1：语音评测失败处理缺失**

- **现状**：SpeechService没有定义失败场景和降级策略
- **影响**：如果讯飞API超时/不可用，用户体验完全断裂
- **建议**：
  ```python
  async def evaluate_with_fallback(
      audio_url: str,
      text: str,
      student_id: str
  ) -> EvaluationResult:
      try:
          return await primary_evaluate(audio_url, text)
      except XFYTimeoutError:
          # 降级策略
          await queue_retry_later(audio_url, text, student_id)
          return EvaluationResult(
              status="pending",
              message="评分稍后返回，请稍候查看"
          )
  ```

**问题2：Redis队列无重试机制**

- **现状**：队列消费者失败后任务丢失，没有死信队列(DLQ)
- **影响**：永久丢失用户评测请求
- **建议**：
  ```python
  # 实现重试策略
  retry_config = {
      "max_retries": 3,
      "retry_delay": 5,  # seconds
      "backoff": "exponential"
  }

  # 死信队列
  DLQ = "speech:eval:dlq"
  ```

**问题3：缺乏熔断和限流设计**

- **现状**：依赖Nginx限流(100QPS)，但应用层无保护
- **影响**：AI服务调用无熔断，可能引发级联故障
- **建议**：
  ```python
  # 引入熔断器
  from circuitbreaker import circuit

  @circuit(failure_threshold=5, recovery_timeout=30)
  async def call_openai(self, prompt: str):
      ...
  ```

#### 📝 可观测性缺失

- ❌ 没有定义日志格式和级别
- ❌ 没有指标采集(metrics)设计
- ❌ 没有分布式追踪设计
- **建议**：集成OpenTelemetry

```yaml
# opentelemetry配置
instrumentation:
  exporters:
    - otlp
    - prometheus
  traces:
    sample_rate: 0.1
  metrics:
    interval: 60000
```

### 2.3 Sam Newman - 分布式系统

#### 🔴 CRITICAL 问题

**问题1：服务间通信模式单一**

- **现状**：所有服务间调用都是同步HTTP
- **影响**：语音评测场景适合异步消息，但当前设计混淆
- **建议**：
  ```
  区分命令和查询(CQRS)
  语音评测使用消息队列完全解耦
  学习报告生成使用后台任务
  ```

**问题2：数据一致性策略缺失**

- **现状**：跟读记录+评分结果涉及多个表
- **影响**：没有定义事务边界和补偿机制
- **建议**：
  ```python
  # 使用Saga模式处理分布式事务
  async def submit_reading_task(audio_url, book_id, page_id):
      async with transaction():
          task = await create_task(audio_url, book_id, page_id)
          await publish_event("reading_task_created", task)
          # 如果后续步骤失败，触发补偿
  ```

**问题3：数据库连接池设计**

- **现状**：没有定义PostgreSQL连接池配置
- **影响**：高并发下可能耗尽连接
- **建议**：
  ```python
  # SQLAlchemy连接池配置
  engine = create_async_engine(
      DATABASE_URL,
      pool_size=20,
      max_overflow=10,
      pool_pre_ping=True,
      pool_recycle=3600
  )
  ```

#### 📝 扩展性建议

- 未来需要支持多租户，建议在数据库层添加 `tenant_id`
- AI服务可以考虑独立部署，便于扩展
- 文件上传应考虑CDN加速

### 2.4 Karl Wiegers - 需求完整性

#### 🔴 CRITICAL 问题

**问题1：JWT Token过期时间未明确**

- **现状**：认证流程中提到 `expires_in: 7200`，但refresh token策略不清晰
- **影响**：用户会话管理不明确
- **建议**：
  ```python
  # Token配置
  ACCESS_TOKEN_EXPIRE_MINUTES = 30   # 30分钟
  REFRESH_TOKEN_EXPIRE_DAYS = 7      # 7天

  # Refresh流程
  POST /api/v1/auth/refresh
  Body: {"refresh_token": "xxx"}
  Response: {"access_token": "new_xxx"}
  ```

**问题2：每日3次限制实现不明确**

- **现状**：需求提到免费版每日3次跟读，但API设计和数据库模型没有体现
- **影响**：功能无法正确实现
- **建议**：
  ```sql
  -- 修改subscriptions表
  ALTER TABLE subscriptions
  ADD COLUMN daily_reading_count INT DEFAULT 0,
  ADD COLUMN last_reading_date DATE;

  -- 业务逻辑
  async def check_daily_limit(user_id):
      sub = await get_subscription(user_id)
      today = date.today()

      if sub.last_reading_date != today:
          sub.daily_reading_count = 0
          sub.last_reading_date = today

      if sub.daily_reading_count >= 3:
          raise DailyLimitExceededError()
  ```

**问题3：错误处理场景缺失**

- **现状**：API设计没有定义错误响应格式
- **影响**：客户端无法统一处理错误
- **建议**：
  ```python
  # 统一错误响应格式
  class ErrorResponse(BaseModel):
      code: str          # 错误码
      message: str       # 错误信息
      details: dict      # 详细错误信息
      request_id: str    # 请求追踪ID

  # HTTP状态码规范
  400 - 参数错误
  401 - 未认证
  403 - 无权限
  404 - 资源不存在
  429 - 请求过于频繁
  500 - 服务器错误
  ```

#### 📝 需求可追溯性

- ❌ 功能需求没有对应到具体API和数据库表
- **建议**：创建需求追踪矩阵(RTM)

## 四、架构决策确认

### ✅ 正确的设计决策

1. **模块化单体架构** - MVP阶段完全正确，避免分布式复杂度
2. **技术栈选择** - FastAPI + SQLAlchemy + PostgreSQL 是成熟方案
3. **Redis队列** - 适用于异步评测场景
4. **JWT + RBAC** - 认证授权设计合理
5. **腾讯云COS** - 适合小程序文件存储

### ⚠️ 需要澄清

1. 文档声称"微服务架构"但实际是单体 - 需要统一术语
2. 部署图使用K8s但MVP用Docker Compose即可 - 避免过度设计
3. Elasticsearch列入技术栈但未在设计中体现 - 确认是否需要
